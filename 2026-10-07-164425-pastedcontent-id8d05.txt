     1. Context and plain-language summary

     Joplin's database code (packages/lib) builds SQL by gluing text together.
     About 480 SQL snippets live in 50 files. Kysely is a library that builds
     the same SQL from typed TypeScript calls, so typos in column names are
     caught by yarn tsc instead of at runtime.

     What I found while exploring:

     - How queries run today. All SQL goes through one class, Database
       (database.ts). It hands the text to a "driver": database-driver-node.ts
       (node-sqlite3, callback style) on desktop and CLI, and
       app-mobile/utils/database-driver-react-native.ts on mobile. better-sqlite
       is only a stub.
     - Kysely cannot run queries on those drivers. Its built-in SQLite support
       expects the synchronous better-sqlite3 object. Joplin uses a different
       library and phone/web drivers. So the proposal is to use Kysely only to
       write the SQL (it turns a query into text plus values) and keep Joplin's
       existing drivers, retry logic and transaction handling to run it. I tried
       this on this machine: Kysely loads from our CommonJS code on Node 22.12
       and produces correct SQLite text.
     - Where the SQL is.
       - BaseModel.ts: generic select, insert, update and delete helpers that
         every model uses.
       - models/*.ts: about 300 hand-written queries (Note, Folder, BaseItem,
         Resource, Revision, Tag, NoteEmbedding, and others).
       - JoplinDatabase.ts: the first-version schema (~120 lines of CREATE
         TABLE) plus an upgrade ladder for versions 1 to 41, and
         refreshTableFields.
       - services/database/migrations/42.ts to 53.ts: newer upgrade steps.
       - services/search/: queryBuilder.ts (builds big UNION/INTERSECT/WITH
         queries) and SearchEngine.ts (full-text search).
       - services/KvStore.ts and a few services (ReportService, RevisionService,
         ResourceService, synchronizer/tools.ts, syncInfoUtils.ts,
         DebugService).
     - Some SQL is passed in from outside the models. Many callers hand
       BaseModel raw fragments such as conditions: ['title LIKE ?'], order, or
       fields. These have to be converted too, or they will stay as text
       forever.
     - Other packages (app-mobile, app-cli) call db.exec/selectAll/selectOne
       directly in a few places, so the public Database API must keep working
       until the end.

     Hard-to-do-with-Kysely items (details and decisions in section 4):
     triggers, FTS4 / spellfix / sqlite-vec virtual tables, FTS functions,
     PRAGMA, and executing on Joplin's own drivers.

     2. Ground rules for every stage

     1. Run yarn tsc in packages/lib, then the full test run: npx -y -p 
        node@22.23.3 node node_modules/jest/bin/jest.js. The baseline is 1,622 
        passed / 15 failed, and the same 15 failures in the same 4 files. A
        stage is only "done" if it ends at exactly that baseline. (If Jest
        prints EPERM ... rename, just rerun.)
     2. Safety net first: characterization tests. Before touching a query, a
        test records the SQL text and values the old code produces for
        representative inputs. After the change the new code must produce an
        equivalent query (see risk R2 on what "equivalent" means). A schema
        snapshot test does the same for the database structure.
     3. One stage = one reviewable chunk. No commits, pushes or history changes
        by me, ever; you decide when to commit.
     4. Repo style from CLAUDE.md: tabs, single quotes, no any, // comments
        only, one describe() per test file, yarn updateIgnored after adding a
        new TS file.
     5. Public method names and return shapes on Database / models do not change
        until the last stage.

     4. Things Kysely cannot do, and what I propose (needs your decision)

     1. Running queries on Joplin's drivers (decision A). Kysely's SQLite
        support needs a better-sqlite3-style synchronous object; Joplin uses
        node-sqlite3 (callbacks), React Native and web drivers, its own
        retry-on-SQLITE_BUSY loop and its own transaction mutex. Proposal: use
        Kysely only to build queries, keep Joplin's own drivers/transactions.
        Alternative: write a custom Kysely driver per platform. That is a much
        larger job, touches app-mobile, and risks transaction behaviour. I
        recommend the first option.
     2. Triggers (CREATE/DROP TRIGGER for the full-text index). Kysely has no
        trigger builder. Proposal: keep the trigger text as a sql raw fragment
        inside the Kysely schema code. Alternative: replace triggers with
        application code, which changes behaviour and is not recommended.
     3. Virtual tables (FTS4 notes_fts/items_fts, fts4aux, spellfix1, sqlite-vec
        vec0). No builder for these either. Proposal: same raw-fragment
        approach, isolated in one file.
     4. FTS query functions (MATCH, offsets, matchinfo, sqlite-vec MATCH ... AND
        k = N, vec_to_json). Proposal: sql template tag inside otherwise-Kysely
        queries.
     5. PRAGMA table_info (default values). Kysely's introspection does not
        return column defaults, which refreshTableFields needs. Proposal: keep
        that one PRAGMA as a raw fragment.
     6. Old upgrade steps (versions 1 to 41, migrations 42 to 53) (decision B).
        Rewriting history is the riskiest part: a subtle change could alter the
        schema for users upgrading from old versions. Proposal (recommended):
        rewrite with Kysely and prove equality with the Stage 11
        schema-comparison tests. Alternative: leave frozen old steps as SQL text
        and write only new migrations with Kysely, which means "not everything"
        is migrated.
     7. ES-module-only Kysely vs. our CommonJS build. Works with require in Node
        22.12 (with an "experimental" notice) as I checked. Whether Jest,
        Electron and the React Native bundler also accept it must be confirmed
        in Stage 0 (decision C if it fails: pin a different loading approach or
        ask you).
